# Elicitation — ask once, in an order and with options the Harness owns

Absorbed on 2026-11-18 from the Regent's Poka-Yoke interaction spec: *correctness by construction, not by
instruction.* An agent that is told to remember an answer forgets it, re-asks it or rebuilds it from the
conversation; a question asked through the engine depends **structurally** on the value the engine stored.
Engine: `scripts/elicit.py`. Adapter: `scripts/hook-elicit.py`. Worked example, also the self-test's acceptance
scenario: `library/examples/elicitation-rule-selection.json`.

It carries conventions §3 into code: answers recorded with their date and source, the newest in force, the one it
replaced kept; never deduce what the Regent did not say.

## 1. The model

| Part | Is | Where |
|---|---|---|
| schema | a declarative JSON graph: each question owns one parameter slot, reads others, holds 2–4 options | a file: shipped with regency, or generated by a regency script |
| state | each slot's canonical value, status, revision, provenance and dependency fingerprint | the one store, tables `elicit_*` (`library/shortcuts.md` §3) |
| scheduler | which questions are eligible now, in `order` | `elicit.py next` |
| renderer | the prompt with `{slot}` replaced by the stored value's label | `elicit.py next` |
| validation | the answer against the options that hold now, the source against its authority, the transition | `elicit.py submit`, the hook |
| adapter | the pop-up: refuse a wrong question before it shows, record the Regent's answer after | `hook-elicit.py` |

A question is eligible only when every slot it reads is resolved and its condition holds:

```text
eligible(q) = all(resolved(s) for s in reads(q)) and holds(q.when) and status(q) not in {answered, skipped}
```

`reads(q)` is computed, never declared alone: `depends_on` plus every `{slot}` in the prompt plus every slot a
condition of the question or of one of its options names.

## 2. The schema

```json
{ "schema": "rule-selection", "version": 1, "about": "...",
  "inputs": {"<slot>": "why: filled only by a derived source"},
  "questions": [
    { "id": "Q_BASE", "slot": "base_option", "header": "Base", "order": 10,
      "prompt": "For the selected rule ({rule}), which option should be used as the base?",
      "depends_on": ["rule"],
      "when": {"param": "rule", "in": ["A", "B"]},
      "options": [ {"value": "X1", "label": "X1", "description": "X1 as the base"},
                   {"value": "Z1", "label": "Z1", "description": "...", "when": {"param": "rule", "equals": "B"}} ],
      "other": false, "multi": false, "required": true, "derived": false } ] }
```

| Field | Rule |
|---|---|
| `header` | 1–12 characters, unique in the schema: the pop-up's chip; the hook recognises the question by it together with its wording or its options (§5) |
| `options` | 2–4 (the pop-up's limit), each with a value, a label and a description; an option's `when` hides it while false |
| `other` | a typed answer is accepted as the value; otherwise only an option's value or label is |
| `multi` | the value is the sorted list of the chosen option values |
| `derived` | a script may set the slot (status `derived`); without it, only the Regent's answer resolves it |
| conditions | `{"param": s, "equals": v}`, `not_equals`, `in`, `not_in` (lists), `exists` (true/false), `{"all": [...]}`, `{"any": [...]}` — data, never code; nothing is evaluated, imported or run |

`python scripts/elicit.py check <schema>` refuses, with one line each: unknown keys, duplicate ids, headers or
values, a slot with two owners, a malformed `{placeholder}`, a slot nobody asks (unreachable), a condition on a
value the owning question can never give, a cycle, a condition that is not one of the operators above.

## 3. States and authority

| Parameter status | Set by | Resolves a dependency |
|---|---|---|
| `confirmed` | the Regent's answer to the pop-up, read by the hook — the only way | yes |
| `derived` | a script, for a slot the schema declares `derived` | yes |
| `proposed` | an agent (`submit --source agent`) | **no**; it never replaces a confirmed value |
| `invalidated` | the engine, when a slot the answer read changed value | no: asked again, its old value kept |

`submit` refuses `--source regent`: an agent cannot type the Regent's answer. A question's status is computed,
never stored: `blocked` (waits on a slot, names which), `skipped` (its condition does not hold), `eligible`,
`presented`, `answered` (its fingerprint — the values and revisions of every slot it reads — still matches),
`reopened` (answered, and the Regent asked to change it: `elicit.py reopen --because "<their words>"`),
`invalidated`.

**Change.** A new value raises the slot's revision and invalidates, in the same transaction, only the slots that
read it, directly or through another dependent; each keeps its value, its history (what, why, which upstream
revision) and returns to the queue. The same value again changes nothing. Every transition runs inside one
`BEGIN IMMEDIATE` transaction: concurrent writers wait, and a failure leaves the state as it was.

**Scope.** A session is one schema version and one task (`EL-####`, `library/ids.md`). Its answers are task
parameters, never project knowledge: they reach an axis only through the command that owns that axis (triage
writes nothing a pass found until the Regent answered). An open session never moves to another version of its
schema: reset it first. The stored schema is checked against its hash at every load. Two open sessions may hold the
same question (one schema started under two tasks, two days of triage): each time the hook sees a pop-up entry it
matches the entry to one session only, the one whose rendering the entry carries and, among equal renderings, the one
that rendered it last (§5); the denial, the count and the answer are recorded in that session alone, never in both.

**Limit, stated: identical renderings asked interleaved.** The pop-up carries no session identity, so two renderings
that are identical (the same question under the same upstream values) cannot be told apart. When they are asked
interleaved (session A renders the question and asks it, then session B renders the same question before the Regent's
answer arrives), `PostToolUse` matches the entry to B, the session that rendered last: the answer is recorded in B,
under B's task, and A's question is left unanswered, still to ask. The trigger is another agent working on the same
repository, or `next` run on B before A's pop-up is asked.

## 4. The protocol

1. Start: `python scripts/elicit.py start <schema> --task <unit or label>` (resumes the open session of the same
   schema and task).
2. Ask: `python scripts/elicit.py next --session EL-#### --wave 4` and pass `ask.questions` to AskUserQuestion
   exactly as given — the wording and the options are the engine's.
3. The hook records the Regent's answers; its context line says what was accepted, refused or invalidated and what
   is next. Repeat 2 until `complete`.
4. The Regent changes an earlier answer in chat: `elicit.py reopen` with their words, then ask it again (2).
5. The consumer reads the confirmed values (`elicit.py status`), never the conversation.

A question an active schema defines is never re-invented in prose, never asked twice under the same fingerprint,
and never taken as answered because the agent proposed a value.

## 5. The hook contract

`hook-elicit.py` on `AskUserQuestion` (`library/hooks.md` §1). An entry is an engine question when an open
session's schema has a question with that header **and** the entry carries either the wording the engine renders for
it now or only labels of that question's options; an entry that shares the header alone is another question. Every
other question passes untouched and nothing is recorded for it, and a project without elicitation sessions is never
written to.

When several open sessions hold the question, the entry belongs to the session whose current rendering it carries,
then to the one that rendered it last (`elicit.py next`), then to the one updated last, then to the one with the
higher session id: the denial, the count and the answer go to that session alone (the limit this leaves is in §3).
Where the hook recognises an entry and where `PreToolUse` checks it against the engine's rendering, wording is
compared with every run of whitespace (spaces, tabs, line breaks) counted as one space, on both sides.

The `PostToolUse` answer lookup does not normalise whitespace: an answer is found only under the entry's question
text exactly as the entry carries it, as a key of `answers` or quoted in the result text. An answer keyed or echoed
with other spacing is not found: the context line says `<question id>: no answer`, or that no answers reached the hook;
nothing is confirmed, and the question stays to ask.

| Event | Does |
|---|---|
| `PreToolUse` | `deny` an engine question that is answered and not reopened (counted `repeat_denied`), blocked, skipped, worded, optioned or multi-selected otherwise than the engine renders it, or sent with its answers filled in; the reason carries the rendering to use |
| `PostToolUse` | each answer through `elicit.record_answer`, into the session the entry belongs to; one context line |

Answers are read from `tool_input.answers`, then `tool_response.answers`, then the `"question"="answer"` result
text, split on the known question texts so an answer holding quotes or commas is read whole. No answer reaching the
hook confirms nothing: the questions stay eligible.

**Limits, stated.** A question asked in plain chat reaches no hook: the guard covers the pop-up only, which is why
the protocol asks through it. An engine question reworded and re-optioned at once is not recognised: it passes, and
its answer confirms nothing. A surface that never delivers answers to `PostToolUse` cannot confirm anything; the
context line says so. An agent with a shell could write the store directly: the store is a cache the hooks and
scripts own, and the events table keeps every transition for audit. The guard fails closed (`onFailure: block`);
when it cannot run, the pop-up is blocked rather than asked unprotected.

## 6. Consumers

| Consumer | Schema | Reads back |
|---|---|---|
| `/regency:repository-analytics-triage` | `python scripts/analytics.py triage-schema [ids \| --pass AN-##]`: per live finding, the disposition, then the axis of a promotion or the reason of a trash | `analytics.py triage --from-elicit EL-####`: only `confirmed` answers from the Regent; it leaves the session open. Closing it once its `undecided` list comes back empty is a step of the triage playbook, which the agent runs: `elicit.py reset --session EL-####` |

A schema extension an agent discovers is checked and kept as proposed (`elicit.py propose <schema> --onto
EL-####`): it never activates itself. A schema becomes active only as a file the Regent ratified, or as the output
of a regency script.

## 7. Measures

`elicit.py status` counts per session: questions presented, answers accepted, refused and unchanged, parameters
invalidated, and `repeat_denied` — the repeated questions the guard avoided.
